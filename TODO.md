## Phase 1 — Backend core

- **`AuthModule` (Telegram `initData` validation + JWT issuance) has not been tested end-to-end with a real bot token or real `initData` from a live Telegram Mini App.** Verified instead via: 11 unit tests in `apps/api/src/auth/telegram-init-data.spec.ts` covering the HMAC validation algorithm (accept/reject/tamper/expiry/replay cases), using a synthetic constant token (`"123456:TEST-bot-token-not-real"`) and initData signed locally by a test-only helper — not a real bot token, not real Telegram-issued initData. There is no integration/e2e test exercising `AuthController` → `AuthService` → JWT issuance → user creation as a real HTTP request. **Action needed (must be done by the user, who has network access to `api.telegram.org`, before any production deployment):** test the real end-to-end path — open the Mini App inside real Telegram, let it send real `initData` signed with the real `TELEGRAM_BOT_TOKEN` to `POST /auth/telegram-webapp`, and confirm a valid JWT is issued and the correct user is created/found.

## Phase 4 — Ad wizard

- **"My Ads" (`apps/miniapp/src/pages/MyAds.tsx`) has no edit UI for `DRAFT`/`REJECTED` ads**, even though they're editable server-side (`AdService.update`, `docs/DECISIONS.md` ADR-010). `docs/ARCHITECTURE.md` section 5's endpoint list has no `GET /ads/:id` (only list/create/update/submit/stats), so there's no way to fetch an existing ad's full targeting details (categories, channel handles) to prefill the wizard for editing. Rather than unilaterally adding an undocumented endpoint, this was left as a gap. **Action needed:** decide whether to add `GET /ads/:id` (small, low-risk addition) or handle editing some other way, then wire up an edit entry point from `MyAds.tsx`.
- ~~`AdService.submit()`'s wallet-balance check is a point-in-time gate, not a reservation.~~ **Resolved 2026-08-27** — `submit()` now atomically reserves the budget (real wallet debit, not just a check), and `AdService.reject()`/`cancel()` refund the unspent remainder. See `docs/DECISIONS.md` ADR-013 and `docs/ARCHITECTURE.md` section 4.1.
- **`AdService.reject(adId, reason)` exists and is tested (ADR-013) but has no HTTP endpoint** — there's no `AdminModule`/admin auth yet (phase 6). **Action needed in phase 6:** when building `POST /admin/ads/:id/reject`, call this method directly rather than reimplementing the refund logic.

## Phase 5 — Ad Serving Engine

- **`excludedCountries` targeting (docs/ARCHITECTURE.md section 4 step 3) is a documented no-op.** `AdServingService.serveAd()` has no viewer-country input to filter on - `apps/bot` doesn't have/pass this either. **Action needed:** decide where viewer country comes from (Telegram doesn't expose it directly to bots) before this filter can do anything.
- **`GET /serve/ad`/`POST /serve/click` are protected by one shared `INTERNAL_SERVICE_TOKEN` (docs/DECISIONS.md ADR-015), not real per-publisher API keys.** This is fine while only `apps/bot` calls them, but not once phase 7's external "SDK for other bot owners" (docs/PRD.md section 2.6) exists. **Action needed in phase 7:** design real per-channel API keys issued at channel registration, and migrate these two endpoints off the shared token.
- **`apps/bot` doesn't actually call `GET /serve/ad`/`POST /serve/click` yet** - `ServeModule` was built and verified directly via HTTP with a manually-inserted test `Channel` row (no `POST /channels` exists yet - phase 7), not through any real bot flow. **Action needed:** once phase 7 gives channels a real registration path, wire `apps/bot` to actually serve ads into a channel's posts using these endpoints.
- **No advertiser notification when an ad hits `OUT_OF_BUDGET`** (docs/ARCHITECTURE.md section 4 step 8 wants one). `apps/api` has no push channel into `apps/bot` (`apps/bot` only long-polls Telegram; nothing calls it from the API side) - this is a cross-app integration gap, not solved in phase 5. **Action needed:** design how `apps/api` tells `apps/bot` to message a user (a queue, a shared DB table it polls, a direct HTTP call to a small endpoint on the bot process, etc.) before this can be built.
- **The `dailyViewLimitPerUser` check (`AdImpression.count` then compare) has a narrow race window** under concurrent requests for the same ad+viewer - unlike the budget deduction, which is atomic via a conditional `updateMany` (docs/DECISIONS.md ADR-015). Worst case is a viewer seeing one extra impression of the same ad in a rare race, not a money-safety issue, so left as a known minor limitation rather than adding per-viewer-per-ad locking now.
